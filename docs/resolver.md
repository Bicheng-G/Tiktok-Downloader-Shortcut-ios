# 解析路径与实测记录

研究日期：2026-09-24。目标是公开抖音视频链接 → 可下载 MP4，供 iPhone Shortcut 调用。

## 为什么 HTTP 优先，同时保留浏览器

通过 Browser Use 打开精选页，播放器 `currentSrc` 是 `blob:`，不是可分发地址。独立 Playwright 会话捕获的 `/aweme/v1/web/aweme/detail/` 等响应包含作品 ID、视频信息和带签名的 CDN 地址。网页自身执行 JS、建立匿名会话并生成请求参数；不需要读取用户个人浏览器的 Cookie。

直接 HTTP 取 PC 页面，在当前网络环境得到约 72 KB 的 JS 挑战页面；手机分享页得到 `_ROUTER_DATA` 框架，但缺少 `videoInfoRes` 和视频地址。简单直接请求 PC detail API 返回 `403 / Uifid Not Found`。这些结果只能说明本次测试条件，不能证明所有 HTTP 实现都不可能成功。

根据 [media-parser 的移动端接口研究](https://github.com/ucmao/media-parser/blob/main/docs/parsers/douyin.md) 独立实现并实测两条固定的 HTTP 路径：

```text
https://api5-normal-c-hl.amemv.com/aweme/v1/feed/?aweme_id=<id>&aid=1128
https://aweme.snssdk.com/aweme/v1/feed/?aweme_id=<id>&aid=1128
```

手机分享样例可返回目标作品；网页版样例两个节点都返回 HTTP 200，但列表中只有其他推荐作品。改变移动 UA 或少量 feed 参数也未命中网页版样例。因此不能取列表第一项，更不能将 200 算作解析成功。未使用研究项目宣称的成功率作为本项目成功率，也未复制其签名或凭据代码。

最终实现先精确匹配 ID，再读取 MP4 候选；HTTP 无匹配时复用单个浏览器兜底。浏览器会保持自己的匿名 context，每次关掉任务页面；进程崩溃后在下次请求重建。这个方案消除了每次 API 请求都启动浏览器的成本，但没有宣称完全去掉浏览器依赖。

## CDN 与文件验证

- 观测到的 CDN 包括 `v3-dy-o.zjcdn.com`、`v5-dy-ov-experiment.zjcdn.com`、`v11-o.douyinvod.com`。
- 元数据同时包含 MP4 和 DASH；排除 `media-video-*`、`media-audio-*` 等分离轨道以及 HLS，不误取编解码探测文件。
- 默认优先 H.264，再按分辨率和码率排序。保留签名原文，不通过替换域名或 `playwm` 猜下载地址。
- 用 Range 读取文件头，最多探测 4 个排序后的候选；接受合法 200 或从 0 开始的 206，检查 `ftyp`。
- CLI 下载使用独立 HTTP 会话、随机 `.part`、长度与 MP4 检查，完成后原子改名。API 只返回地址与请求头；iPhone 负责真正下载。
- `download_addr` 是最后备用项，可能带水印。本项目不保证所有作品的水印状态、最高画质或原始文件。

## 最终后端实测

通过新版 FastAPI 应用处理真实输入，再在独立 Requests 会话下载，使用 ffprobe 检查完整 MP4。

| 输入 | 视频 ID | 实际路径 | 首次解析 | 文件字节数 | 音视频 |
| --- | --- | --- | ---: | ---: | --- |
| 完整手机分享文案 / `v.douyin.com/p-rXmps4nWc/` | 7680575887263617273 | HTTP | 5.86 s | 62,814,578 | 576×1024 H.264 + AAC，566.983 s |
| `jingxuan?modal_id=7688235974236654911` | 7688235974236654911 | HTTP 未命中 → 浏览器 | 37.03 s | 98,571,586 | 1920×1080 H.264 + AAC，784.958 s |

再次请求网页版样例：缓存命中 0.02 秒；`refresh:true` 重新解析 15.33 秒。两次浏览器解析共启动 **1 个浏览器进程**。这是小样本、单机、单网络的观测，不是延迟承诺。

HTTP 样例的画质低于早期浏览器路径的 1080×1920 / 88,267,701 字节版本，这是响应提供的候选不同所致。当前产品选择较轻的 HTTP 优先；若希望比较画质，可显式使用 `browser` 模式。

此前浏览器原型还完整下载了 `7686432847778982833`（16,393,655 字节）和 `7684003553698008372`（110,569,964 字节），均为 1920×1080 H.264 + AAC。它们不构成任意链接都可用的证据。

本地原始响应和报告在 Git 忽略的 `artifacts/`，视频在 `downloads/`，不进入公开仓库。测试不依赖这些本地文件。50 项离线测试覆盖输入、安全域名、ID 匹配、HTTP 未命中、浏览器复用、并发与缓存、下载完整性、API 鉴权及生成 Shortcut 的引用与配置。

## 容器验证

两种 Docker 镜像都已成功构建和启动，并通过真实 Uvicorn 端口请求。测试容器使用非 root 用户，内存上限 1 GB、共享内存 256 MB。

| 镜像 | 输入 | 实际路径 | 解析耗时 | 结果 |
| --- | --- | --- | ---: | --- |
| `http` | 手机短链接 | HTTP | 3.52 s | 200，正确 ID，MP4 头验证成功 |
| `auto` | 手机短链接 | HTTP | 3.86 s | 200，正确 ID，MP4 头验证成功 |
| `auto` | 网页 `modal_id` | Linux / Chromium 兜底 | 14.12 s | 200，正确 ID，MP4 头验证成功 |

所有返回地址还在容器外的独立 HTTP 会话通过 Range / MP4 头检查。健康检查、未授权 401、Compose 配置和 Python wheel 打包也通过，测试容器已停止并自动移除。

首次容器测试曾出现一次主机端口未能及时连接、一次 `BROWSER_ERROR`。随后独立 Chromium 诊断及同镜像完整复测成功；未为此改变解析逻辑，浏览器失败的具体根因未确定。这说明成功记录不能等同于持续稳定性保证。CI 配置会构建两种镜像、检查健康状态并验证 Chromium 能启动，但不自动对抖音运行网络测试。

## 未验证与限制

尚未在实体 iPhone 导入、下载或保存 Photos，也未测试不同公网 IP 下手机使用服务器解析出的 CDN 地址。部署后应先用手机执行两个样例。

上游接口、签名和 CDN 可能变化，云服务器 IP 也可能被拒绝。已过期、私密、下架、地区受限或要求验证的作品不保证成功；只支持完整 MP4，暂不合并 DASH 或处理图文、直播。错误不会用其他推荐视频代替目标作品。
